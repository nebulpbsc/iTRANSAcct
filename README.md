# iTransAcct — Single Data Entry, Dual Bookkeeping

A B2B accounting platform where two independent companies complete a full
transaction — invoice → sales voucher → transmission → acknowledgment →
purchase voucher → posted books on both sides — with data typed exactly
**once**. No manual journal entry screen exists anywhere in the product;
every ledger posting is auto-generated by the state machine below.

```
DRAFT ──send──> SENT ──take──> TAKEN
(pink)          (green)         (blue)
                   │
                   └──reject──> REJECTED
```

- **DRAFT**: only the initiator (sender) can see/edit it. No accounting impact.
- **SENT**: sender transmits it. A journal entry is auto-posted to the
  **sender's own books** at this instant (Sale, or Payment). The transaction
  now appears, read-only, in the counterparty's Inbox.
- **TAKEN**: recipient acknowledges with **one click — zero data entry**
  (except, for payments, picking which of their own bank/cash accounts
  received the funds). A mirrored journal entry auto-posts to the
  **recipient's books** (Purchase, or Receipt).
- **REJECTED**: recipient declines; nothing posts on their side.

Because both legs post equal-and-opposite amounts against each other's
party ledger, the **Reconciliation** report needs no manual matching — it
just compares "as per our books" vs. "as per their books."

## Stack

- **Backend**: Python, FastAPI, SQLAlchemy ORM, SQLite by default
- **Frontend**: React (Vite), React Router, plain fetch (no heavy UI kit)
- **Database**: SQLite out of the box; swap to Postgres by setting one
  environment variable (see below) — no code changes needed, since every
  query goes through the ORM.

## Running it locally

### 1. Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
uvicorn app.main:app --reload   # http://localhost:8000
```

This creates `itransacct.db` (SQLite) automatically on first run and
exposes interactive API docs at `http://localhost:8000/docs`.

Optional — populate two demo companies and walk a full Sale + Payment
cycle through both books:

```bash
python seed_demo.py
```

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev                     # http://localhost:5173
```

The Vite dev server proxies `/api/*` to the FastAPI backend on `:8000`,
so there's no CORS configuration to fight with in development.

### 3. Try the workflow

1. Register two companies (or run `seed_demo.py` to get two pre-made ones).
2. In Company A, go to **Connections**, paste Company B's connect code.
3. In Company A, go to **New Transaction** → choose **Sale**, fill in items
   once, save as draft, then **Send**. This auto-posts a Sales voucher to
   Company A's own books.
4. Log in as Company B, go to **Inbox**, click **Take** — zero typing. This
   auto-posts a mirrored Purchase voucher to Company B's books.
5. Check **Ledger**, **Trial Balance**, **Receivables/Payables**, and
   **Reconciliation** on both sides — all live-computed, nothing manual.

## Moving to Postgres

Set one environment variable before starting the backend:

```bash
export DATABASE_URL="postgresql+psycopg2://user:password@host:5432/itransacct"
```

Then uncomment `psycopg2-binary` in `requirements.txt` and reinstall. Every
model and query in this codebase is written against the SQLAlchemy ORM
(no raw SQLite-specific syntax anywhere), so this is the only change
required.

## Accounting logic reference

Each company gets its own independent chart of accounts, auto-provisioned
on registration (`Sales Account`, `Purchase Account`, `Cash Account`), plus
one party ledger per counterparty, created lazily the first time it's
needed.

**Sale/Purchase, on Send** (sender = seller):
```
Dr  Party Receivable (counterparty)      total
    Cr  Sales Account                        total
```

**Sale/Purchase, on Take** (recipient = buyer):
```
Dr  Purchase Account                     total
    Cr  Party Payable (sender)               total
```

**Payment/Receipt, on Send** (sender = payer):
```
Dr  Party Payable (counterparty)         amount
    Cr  Cash/Bank Account                    amount
```

**Payment/Receipt, on Take** (recipient = payee):
```
Dr  Cash/Bank Account                    amount
    Cr  Party Receivable (sender)            amount
```

## Notes / next steps for a production build

- **Auth**: JWT is intentionally simple here (single shared secret, no
  refresh tokens). For production, add refresh-token rotation and
  per-company API keys for any machine-to-machine integrations.
- **Multi-user companies**: currently one login = one company. Add a
  `CompanyUser` join table with roles (Admin/Accountant/Viewer) if multiple
  people need to log into the same company.
- **Reversals/amendments**: TAKEN transactions currently can't be edited
  (correct, for audit integrity) — add an explicit "Debit Note / Credit
  Note" transaction type for corrections rather than mutating history.
- **Tax handling**: line items don't currently compute GST/HST/PST. Add a
  `tax_rate` per line and a dedicated "Output Tax" / "Input Tax" account
  pair in `posting.py` when you're ready to model it.
- **Notifications**: Inbox currently requires polling. Add webhooks or
  WebSocket push if you want real-time badges instead of refresh-on-load.
